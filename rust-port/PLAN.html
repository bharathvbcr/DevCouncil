Section 01

What changed in this revision

Two directives reshape the plan. The rewrite is clean-room — a standalone Rust implementation, not a PyO3 extension wrapping the existing design. Nothing is ported function-by-function and no Python survives in the indexer. Token efficiency becomes a first-class requirement rather than an afterthought, which is a substantive change: it is the one dimension where the current system is worst, and it was invisible in the previous plan.

The consequence for the findings is clarifying. Under a hybrid port, each defect needed a fix and a migration. Under a clean-room rewrite the findings are the specification — the new system is designed so they cannot occur, and each one becomes an acceptance test rather than a patch. The distinction that mattered before, whether Rust "fixes" a defect or "inherits" it, collapses into a single question: is it written into the spec, or will it be rebuilt by accident?

One consequence to price in honestly: a clean-room rewrite delivers no value until cutover. The previous plan front-loaded four Python fixes that would have taken resync under 500 ms within weeks. That option is now off the table by choice, and the 35-language matrix — 2.5× GitNexus's coverage, 1.75× CodeGraph's — sits on the critical path from day one.

Two additions since: seven reference-derived enhancements (§3, R1–R7) drawn from GitNexus and CodeGraph, and §4, an inventory of capabilities that must survive. The second is the more important of the pair. A specification says what must become true; nothing until now said what must stay true, and a clean-room rewrite loses undocumented behaviour without any signal that it has.

Section 02

Token cost — the unmeasured surface

dev map exists to give agents context. Its own output is therefore a budget item, and nothing in the system accounts for it. Token figures below are byte counts at four characters per token — an estimate, but the magnitudes are not in question.

The project's own instructions direct agents to open it first. Two keys carry 78% of the cost: dependents at 63,844 tokens across 406 entries, and files at 35,512 across 853. Design rule for the rewrite

No agent-facing surface emits an unbounded response. Every query takes a token budget and returns { shown, total, truncated } so a partial answer can never be mistaken for a complete one. Wholesale artifact reads are replaced by queries — the map becomes something you ask, not something you load.

Section 05

Target architecture

A single Rust binary that owns indexing, storage, watching and the agent interface. CodeGraph validates the shape: Rust kernel, tree-sitter compiled in, plain SQLite with FTS5. The storage engine does not need to change — SQLite is 3% of the current build — so the rewrite spends its risk budget on the parts that are actually wrong.

binary surface 
devmap serve     // long-lived: watcher + index + MCP over stdio/socket
devmap build     // one-shot index, for CI
devmap query …   // CLI queries, token-budgeted like the MCP surface
devmap status    // freshness, generation, lock holder
workspace 
crates/
  devmap-extract/   // tree-sitter, one module per language, rayon
  devmap-resolve/   // symbols, calls, receiver types, imports
  devmap-analyze/   // liveness, dead code, Leiden clustering, PDG
  devmap-store/     // rusqlite, v3 schema, generations
  devmap-query/     // token-budgeted responses
  devmap-serve/     // watcher, daemon, MCP
  devmap-cli/       // binary entry point

The 37 Python consumers do not import a shim — they talk to the daemon. A thin client of roughly 400 LOC replaces 26,837, exposing the same call signatures the verification checks and MCP handlers already use, over a versioned local socket. That client is the only Python that remains, and it contains no analysis logic.

Making the daemon the sole ingestion path is what turns three findings into structural impossibilities rather than fixes. B1 (lost pending work) cannot occur when the queue lives in a process that does not exit. N8 is satisfied by construction. And B4 — readers blocked by the writer — dissolves because the daemon holds the write connection and readers use WAL snapshots.

Section 06

Plan

Six phases. The first freezes observable behaviour so the rewrite has something to be correct against; the last deletes the Python. Estimates assume one engineer and are inferred, not derived from comparable work in this repository. No phase before cutover ships user-visible value — that is the cost of the clean-room choice.

Phase 1

Freeze the contract

est. 4–5 weeks

Capture what the current system produces before replacing it. Build the golden corpus spanning all 35 languages, snapshot canonical graphs from the Python implementation, and write down the 37 consumer contracts — especially the verification checks, whose assumptions about graph shape exist nowhere but their assertions. Add the token budget to the contract now, so the new surface is designed against it rather than retrofitted.

Complete the §4 inventory, then build the corpus from it. Today that inventory covers only the 49% of the subsystem the audit opened; the areas in §4.5 have none at all. Every row in §4 names a corpus requirement, and a capability whose requirement is absent from the corpus is a capability parity cannot protect. This is the phase where an unwritten behaviour becomes a test — or becomes a future regression.

Gate — §4 inventory complete for all 26,837 LOC; corpus satisfies every stated requirement; golden graphs for 35 languages; every consumer contract has a signature and a test; token budgets specified per surface; scoping decision recorded for each §4.5 area (port / keep in Python / drop).
Phase 2

Extraction

est. 6–10 weeks

Tree-sitter for all 35 languages including Python, resolving D1 by construction — one extractor, no stdlib-ast path. Parallel by default with rayon, pools sized from real cores (B12, N9). Grammars link into the binary, so the spawn-based crash isolation, the 30s per-file timeout and the quarantine-and-respawn logic have no analogue to port: a panicking grammar unwinds one task.

Gate — extraction parity against golden corpus, all 35 languages; near-linear core scaling; Python-extraction divergences enumerated and individually accepted.
Phase 3

Resolution and analysis

est. 10–14 weeks

The largest and hardest phase — 76% of current build time, and global passes with subtle ordering semantics. B13–B15 have no counterpart in a design built on interned FileIds and a single tree traversal. Fold in the quality work while the code is open: Leiden with cohesion scores (N5, R6), constructor-inferred receiver types (N6), dynamic-dispatch hops in call paths (R5), and explicit status on any analysis that times out (N4). R5 builds directly on N6 — once a receiver's type is tracked, an interface-dispatch hop becomes resolvable rather than a dead end — so they are one work item, not two.

Gate — full-graph parity on the corpus; cold build for this repo under 2s; resolution precision ratchet meets or beats the Python baseline; every community reports cohesion; interface-dispatch path resolves in corpus.
Phase 4

Store and daemon

est. 5–7 weeks

v3 schema with interned paths (B10), clean primary keys (B9), indexable FTS pruning (B6), O(1) cache admission and liveness-ordered eviction (B7, B8), scheduled vacuum (B11), one schema with no rollback shadow (D2), WAL auto-checkpoint tuned for build churn (R4). Differential membership writes with deletion reconciliation — B3 and N2 are one work item and must never be separated. The daemon owns the watcher and a durable queue, and exposes targeted repair so a corrupt search index does not force a full rebuild (R7).

Gate — 1-file edit writes <100 rows at 10k files; kill −9 mid-build replays; index <60 MB for this repo; freelist <5% without manual vacuum; devmap repair --fts rebuilds the search index alone; freshness holds across a 30-minute multi-session burst.
Phase 5

Token-budgeted query surface

est. 5–6 weeks

The graph stays resident in the daemon, so N1's 1,639 ms reload has no analogue. Every response takes a budget and reports truncation. The 129k-token repo map is replaced by a ≤2k-token manifest plus queries; the 17.4 MB export becomes opt-in and moves out of the context directory (T1–T3, N3). Add RRF over BM25 and vectors (N7), bounded by a node cap so the embedding index cannot grow without limit (R3), and either implement real graph queries or retire the Cypher shim honestly (N10).

Collapse today's 18 map/graph MCP tools to one primary plus a small unlisted set (R1), and have results carry verbatim source grouped by file (R2). These are the largest remaining token wins and they compound: tool definitions cost context on every request whether or not they are called, and a result without source forces a follow-up read that costs another round-trip.

Gate — explore p95 <50 ms at 10k files; no response exceeds its budget; every truncation reports {shown, total}; manifest ≤2k tokens; ≤3 listed tools; a symbol query answers without a follow-up file read; peak RSS <1 GB at 10k files.
Phase 6

Cutover and deletion

est. 4 weeks

Point the 37 consumers at the client, run both systems in parallel against live work until the parity harness is quiet, then delete indexing/ and codeintel/. Deleting is the phase — a rewrite that lands beside what it replaces doubles the surface permanently, and the 16,534 LOC of existing tests must pass against the new core before the old one goes.

Gate — all existing tests green against Rust; 26,837 LOC removed; no Python analysis code remains; wheels or binaries published for every supported platform.

Total 34–46 weeks. The 35-language matrix in phase 2 and the global resolution passes in phase 3 are the long poles and carry nearly all the schedule risk. Treat the range as a lower bound: it was derived from the 49% of the subsystem the audit opened.

Section 07

Implementation guide

1 · Token budget as a protocol primitive

T1–T4, T3 · phase 1, enforced phase 5

Put the budget in the request type so it cannot be forgotten, and make truncation a value rather than an absence. This is the generalisation of what prompt_builder.py already does correctly for file bodies.

crates/devmap-query/src/budget.rs 
pub struct Request<Q> {
    pub query: Q,
    pub token_budget: u32,   // required — no default that hides cost
    pub min_confidence: Confidence,
}

pub struct Response<T> {
    pub items: Vec<T>,
    pub shown: u32,
    pub total: u32,          // what a complete answer would have held
    pub truncated: bool,
    pub tokens_used: u32,
}

Two rules make this load-bearing. Rank before truncating, so the budget keeps the most relevant rows rather than the first ones. And carry both numbers always — a capped sample presented as complete coverage is how "no dead code found" comes to mean "we stopped looking at 200".

2 · Replace the repo map with a manifest plus queries

T1 · 129k → ~2k tokens

78% of the current map is dependents (63,844 tokens) and files (35,512) — lookup tables shipped whole to answer point questions. Neither belongs in a file an agent reads; both are one query each.

what stays in the manifest — everything under ~2k tokens 
subsystems (names + entry points only)   ~800 tok
important_files                          ~140 tok
entry_roots, languages, test_commands     ~80 tok
freshness: head, fingerprint, generation   ~30 tok
-- dependents, files: removed. queried instead.
what replaces them 
devmap where <symbol>          // one answer, not 853 file entries
devmap deps <path> --budget N  // ranked, truncation reported
devmap impact <symbol>         // precomputed blast radius + confidence

CLAUDE.md changes with it — "open repo_map.json first" becomes "query the map". That instruction is currently the single largest token expenditure in the system, and it is one line of documentation.

3 · Collapse the tool surface, return source with results

R1, R2 · phase 5

Today the MCP surface exposes 18 map/graph tools. Tool definitions are serialised into every request whether or not they are called, so an unused tool is a standing tax on every turn. CodeGraph lists one primary tool and leaves the rest unlisted but callable.

listed vs callable 
Listed (≤3):
  devmap_explore   // symbols + call paths + impact + source, budgeted
  devmap_search    // ranked lookup, budgeted
  devmap_status    // freshness, generation

Unlisted but callable: dead, routes, paths, affected-tests,
                       impact, trace, process, api-impact, …

R2 is the other half. A result that gives only a location forces the agent to issue a file read, which costs a round-trip and usually pulls in far more of the file than the answer needed. Returning the relevant spans inline, grouped by file, makes the query self-contained.

crates/devmap-query/src/types.rs 
pub struct SymbolHit {
    pub id: SymbolId,
    pub path: FileId,
    pub span: (u32, u32),
    pub source: String,      // R2: the lines themselves, budget-trimmed
    pub flows: Vec<FlowRef>, // step 4: processes it participates in
}

Both interact with the budget from step 1: source is the first thing trimmed as a response approaches its limit, and the trim is reported rather than silent.

4 · Precompute so one call is enough

T3 · GitNexus's central idea

The deepest token saving is not compression but avoided round-trips. An agent that must issue four queries and reassemble edges spends far more context than one that receives a structured answer. GitNexus does clustering, process detection and confidence scoring at index time so tool responses are complete; dev map already computes the raw material in its liveness and PDG layers and then discards the structure.

Concretely: store the entry-point-to-leaf call flows at build time, and let a symbol query return the flows it participates in with step indices — not a set of edges the caller must walk. Confidence filtering belongs in the same place: speculative low-confidence edges cost context and mislead, so min_confidence is a request parameter with a conservative default.

5 · Differential writes with deletion reconciliation

B3 + N2 · one work item

This is the 7.55s. Today each generation re-materialises all 59,880 membership rows; it must write only the delta. The hazard is that deletion is currently handled implicitly by the full rewrite, so the delta path has to carry it explicitly or deleted files persist as live nodes forever.

algorithm 
1. carry forward  rows from prev generation whose source file
                  is not in :affected
2. delete         rows whose source file is in :affected
3. insert         freshly resolved rows for :affected
4. reconcile      any file present in the previous generation but
                  absent from `git ls-files` is a deletion — add it
                  to :affected even though nothing on disk changed

Step 4 is the one that is easy to miss and the reason these cannot ship separately. Renames are a delete plus an add under this model — correct, though it loses rename identity, which nothing downstream consumes today.

6 · Schema v3

B6, B9, B10, D2

Interned paths fix the storage bloat and the hot-loop path parsing at once — B10 and B13 are the same problem at two layers. FTS holds text only, with generation membership in an ordinary indexable table so pruning is a bounded delete rather than a full reindex.

core tables 
CREATE TABLE paths (
    id   INTEGER PRIMARY KEY,
    path TEXT NOT NULL UNIQUE
);

CREATE TABLE generation_edges (
    generation_id  INTEGER NOT NULL,
    ordinal        INTEGER NOT NULL,
    payload_hash   TEXT NOT NULL,
    source_file_id INTEGER NOT NULL REFERENCES paths(id),
    target_file_id INTEGER NOT NULL REFERENCES paths(id),
    PRIMARY KEY (generation_id, ordinal)   -- B9
) WITHOUT ROWID;

-- FTS holds text only; membership is indexable
CREATE VIRTUAL TABLE nodes_fts USING fts5(
    name, qualified_name, path, tokenize='unicode61'
);
CREATE TABLE nodes_fts_map (
    rowid_ref     INTEGER NOT NULL,
    generation_id INTEGER NOT NULL,
    PRIMARY KEY (generation_id, rowid_ref)
) WITHOUT ROWID;

CREATE TABLE pending_paths (      -- B1: survives process death
    path       TEXT PRIMARY KEY,
    queued_at  REAL NOT NULL,
    attempts   INTEGER NOT NULL DEFAULT 0
) WITHOUT ROWID;

Pending rows are deleted only after the generation commits, so a crash mid-build replays rather than drops. In the core, FileId(u32) replaces every string path in the hot loops, and the per-edge language classification (B15) collapses into a field resolved once at intern time.

7 · Parallel extraction

B12, N9 · phase 2
crates/devmap-extract/src/lib.rs 
use rayon::prelude::*;

pub fn extract_all(files: &[FileRef]) -> Vec<(FileId, Extraction)> {
    files
        .par_iter()
        .filter_map(|f| {
            if let Some(hit) = cache::get(f.content_hash) {
                return Some((f.id, hit));
            }
            let tree = parser_for(f.language).parse(&f.source)?;
            Some((f.id, extract(&tree, &f.source)))
        })
        .collect()
}

Size the pool from real cores rather than the current min(4, cpu_count()//2). CodeGraph sizes analysis caches from free RAM as well, which matters at 10k files where the Python implementation peaks at 714 MB.

8 · Parity harness

phase 1 · gates every later phase

Structural comparison, not textual — ordinals and iteration order will differ legitimately between implementations. Normalise both sides to sorted sets keyed on stable identity, and run per language so a divergence names the grammar responsible.

canonical form 
nodes: sorted (id, kind, path, line, name, exported)
edges: sorted (source, target, kind, confidence)
dead:  sorted (id, confidence)

Confidence belongs in the comparison. A rewrite that finds the same edges at different confidence changes what the verification gates decide — a behaviour change even though the graph "matches". Expect real divergences from D1; the gate is that each is enumerated and accepted deliberately, not that the count is zero.

9 · Consumer client and distribution

phase 6

The Python client is a transport, not a port: request/response types, a socket, and auto-spawn of devmap serve if it is not running. Roughly 400 LOC with no analysis logic, replacing 26,837. Keeping it that thin is what makes the deletion in phase 6 possible.

Distribution ships the binary per platform — macOS arm64 and x86_64, manylinux x86_64 and aarch64, Windows x86_64 — built in CI on tag. Because grammars link into the binary, this replaces the existing devcouncil-codeintel-grammars companion package rather than sitting alongside it; plan that deprecation deliberately.

Section 08

Risks

  • No value until cutover. 34–46 weeks before anything improves for a user, and the staleness and query-latency problems persist throughout. This is inherent to the clean-room choice, not a flaw in the plan.
  • The estimate is a lower bound. It was derived from the 49% of the subsystem the audit opened. The unread half contains the two largest files (repo_mapper.py, wiring.py) and three concerns with no home in the architecture — see §4.5.
  • The §4 inventory is the thing most likely to be skipped, and most costly to skip. Capability loss from a clean-room rewrite is silent by construction: nothing fails, the graph is merely poorer. The wiring.py exemption rules are the sharpest case — losing one does not break a build, it makes dev map dead report entry points as dead, and a dead-code report nobody trusts is worse than none.
  • The 35-language matrix is the schedule, not the Rust — 2.5× GitNexus, 1.75× CodeGraph, each needing parity evidence.
  • D1 guarantees divergence. Moving Python onto tree-sitter will change extractions. The gate is enumerated-and-accepted, not zero-diff, and someone has to make those calls.
  • B3 and N2 must ship together. Differential writes without deletion reconciliation leave deleted files in the graph permanently — worse than the slowness being fixed.
  • 37 contracts, mostly unwritten. The verification checks encode graph-shape assumptions that exist nowhere but their assertions; phase 1 exists to find them before phase 6 depends on them.
  • Token work is separable. T1–T3 are generated by Python today and could ship in days — a 129k-token artifact reduced to ~2k without waiting for the rewrite. Holding them until phase 5 is a deliberate choice worth revisiting if the schedule slips.
