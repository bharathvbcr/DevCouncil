# `devmap build` performance across four repositories

- binary: `rust/target/release/devmap` — devmap 0.2.1 (store schema 20, code graph schema 2, build `9d8e6db`)
- corpora: local clones pinned at each repository's HEAD, in a disposable scratch directory
- store: a scratch `--db` outside every corpus; no repository's own `.devcouncil/` was read or written
- repeats: 5, round-robin across repositories (minimum reported)
- generated: 2026-09-13T19:50:23+00:00

Earlier entries in this directory measure one repository (DevCouncil) across the
five stages of the retired `map_bench.py` harness. This run instead measures the
three kernel stages across four repositories, to see how cold and incremental
cost scale with corpus size. It drives the kernel directly, as
[`benchmarks/README.md`](../../README.md) prescribes for the live path.

## Stage integrity

Each stage was confirmed to do what its name claims, from the build's own delta:

| stage | delta reported by the kernel |
|---|---|
| `cold` | every file added, 0 unchanged |
| `warm` | 0 added, 0 changed, all unchanged |
| `touch` | exactly 1 changed, the rest unchanged |

`cold` and `touch` produce identical symbol and edge counts on every repository,
so the incremental path reproduces the cold graph rather than merely finishing
sooner.

## Where an incremental build spends its time

scholarlm (4,324 files), minimum per phase across 3 alternating rounds:

| phase | `cold` | `touch` | `touch`/`cold` |
|---|---|---|---|
| `persist:write` | 2.434s | 0.695s | 29% |
| `extract:files` | 1.032s | 0.370s | 36% |
| `resolver:index` | 1.074s | 1.041s | 97% |
| `resolving` (whole tree) | 0.482s | 0.455s | 94% |
| `analyzing edges` (whole tree) | 0.260s | 0.260s | 100% |
| `scan:read` | 0.068s | 0.096s | 141% |
| **total** | **5.405s** | **3.003s** | **56%** |

Persistence and extraction scale down with the change set. Resolution does not:
`resolver:index`, `resolving` and `analyzing edges` together account for roughly
1.76s of the 3.00s `touch` build — about 59% of an incremental build is
whole-tree work independent of how much changed.

This is by design, not a defect. `benchmarks/README.md` records that resolution
"deliberately covers the whole tree so liveness and community detection mean the
same thing on both paths." The number worth carrying forward is the consequence:
on a 4,300-file repository, a one-file edit cannot currently fall below roughly
1.8s, which bounds watcher and hook latency however cheap persistence becomes.

## Caveats

- **The machine was loaded throughout.** A concurrent `cargo test --workspace`
  and a Go test run held the 1-minute load average between 7.5 and 18.1 across
  the sweep's 60 samples, on an 18-core Apple M5 Pro — contended, and at the top
  of that range fully subscribed, but not oversubscribed. Load
  can only make a run slower, so the minimums are the trustworthy statistic;
  the excursion is visible in the max column, where GitPulse `cold` ranges from
  3.060s to 7.261s. Every sample row in the JSON carries its own
  `load1_at_start`. Cross-repository ratios are sound; absolute figures are an
  upper bound on a quiet machine.
- **Per-phase timings need the same treatment as wall clock.** A single verbose
  round taken during the load spike reported `persist:write` at 9.437s against a
  floor of 2.434s — a 3.8x inflation that, read literally, would have said
  persistence dominates incremental builds. Summing the phases and comparing
  against the measured wall clock exposed it (12.3s of phases against a 5.6s
  cold floor is impossible), and the breakdown above is the minimum of three
  alternating rounds instead.
- **`touch` appends one line to one file.** It measures the re-index cost of a
  content change, not the cost of a change that restructures the symbol graph.
- **The corpora are clones at HEAD**, so uncommitted work is excluded — three
  in-flight files in scholarlm were not indexed. Untracked build output that a
  working tree carries is likewise absent.
- **Throughput is not comparable across repositories** as a quality measure:
  files differ in size and language mix, and the resolver's cost depends on the
  call-site density of each language, not on file count.
- **DevType was excluded.** `/Users/bharath/Code/devtools/DevType` holds only an
  empty `.devcouncil/` directory — no source files and no git repository — so
  there is nothing to index.
- This run does not replace `rust/verify.sh`, which remains the required gate
  for determinism, peak RSS, growth plateau and the incremental-vs-cold soak.
