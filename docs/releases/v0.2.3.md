# DevCouncil v0.2.3 Release Notes

DevCouncil v0.2.3 and DevMap v0.2.3 are the same product version. The npm package,
the Go host (`devcouncil` / `dev`), and the Rust workspace (`devmap`, `dcstore`,
`dcverify`, `dcgrep`) all report **0.2.3**.

This is a portability and correctness release, plus one adoption change. It makes
the Windows half of CI able to run at all — it had been red on every push since
2026-09-10, and the failure was masking five crates whose tests had never
executed on that platform — and it fixes the three defects that ran out from
under that mask, two of which reach production rather than only the test suite.
It also fixes the reason a commit, branch switch or rebase could become invisible
to a running daemon.

The store schema stays at **22**. No migration, no rebuild: a v0.2.2 store opens
unchanged.

## Highlights

### 1. Windows checkouts were rewriting the bytes `dc-evidence` digests

`components (windows-latest)` had been red on every push since 2026-09-10.
Eleven `dc-evidence` tests asserted `Passed` and got `Failed`, on Windows only,
naming no cause.

The cause was not in the crate. `dc-evidence` binds a bundle to its contract by
digesting the contract's *exact bytes*, and `fixtures/v1/bundle*.json` record
those digests as literals. The repository had no `.gitattributes`; Git for
Windows installs with `core.autocrlf=true` in its system config, and
`actions/checkout` does not override it. So the Windows checkout wrote
`contract.json` with CRLF, its sha256 changed, and `verify()` took the
`contract_hash != expected.contract_sha256` arm. The JSON still parsed and still
meant the same thing — which is exactly why the failure was silent about its
own reason.

Reproduced on macOS by converting the fixtures and running the suite: the same
eleven test names at the same line numbers, 18 passed / 11 failed, matching the
Windows log exactly. Converting each fixture alone isolates it further —
`contract.json` accounts for 10 and `contract-not-found.json` for 1. The other
six fixtures are unaffected, because only the contracts are digested over raw
bytes.

The fix is a repository `.gitattributes` with `* -text`, not `text=auto eol=lf`:
`benchmarks/results/**` holds recorded competitor stdout that genuinely contains
CRLF, and normalising would rewrite that evidence. `git check-attr` confirms
`diff` and `merge` stay unspecified, so nothing is treated as binary. The file
carries a comment saying so, because a `text` entry added there later re-arms
this bug for whatever it covers.

A new guard checks the whole fixture directory and names line endings and
`.gitattributes` when it trips, so the next reader does not get eleven bare
`left: Failed` assertions.

### 2. That failure was hiding five crates, and three defects came out from under it

`cargo test` aborts at the first failing binary, and `dc-evidence` sorts first.
So `dc-glob`, `dc-proc`, `dc-grep`, `dc-store` and `dc-verify` had **never run**
on `components (windows-latest)` — most of what that job's own comment says it
exists to answer. Only `Build` had been covering them.

With `dc-evidence` green they ran, and three defects surfaced on their first ever
execution. None is a regression from the fixtures fix; each is a defect that fix
made visible.

**Absolute LCOV paths were never reduced on Windows.** `normalise_lcov_path`
tested absoluteness with `starts_with('/')`, which is only ever true on Unix. So
every `C:\...` path llvm-cov and grcov emit took the early return, was never
reduced against the supplied root, and never matched a repo-relative diff path —
every file landed in `coverage_unmeasured`. That is the precise wall the
function's own doc comment says it exists to remove, left standing on the one
platform whose tests did not run. It reaches production through
`dcverify.rs:189`, not just the test.

`has_root` replaces the check: true for `/x`, `C:\x`, `\\?\C:\x` and
`\\server\share`. The prefix match becomes `Path::strip_prefix` compared by
component, so reduction no longer requires the producer and the root to agree on
a separator — the old code built its prefix with a hard-coded `/`, which a
backslash path could never match even after getting past the early return. The
remainder is rejoined with `/`, rebuilt from components rather than by replacing
separators, so a Unix filename that legitimately contains a backslash is not
rewritten.

Component-wise stripping introduces one case the string prefix did not have: an
`SF:` line naming the root itself now strips to nothing. Returning `""` would
file that record's lines under an empty path and read as some *other* file's
coverage, so it is kept verbatim and reported unmeasured, like every other
unreducible path.

**The symlink walk refused everything on Windows.** With coverage red,
`evidence_cli.rs` had never run either; with it green, 4 of its 8 Windows tests
failed on first execution, all with
`{"ok":false,"error":"cannot inspect input: Incorrect function. (os error 1)"}`.

`reject_symlinks` walks a path component by component and stats each accumulated
prefix. The first component of an absolute Windows path is the *drive prefix*,
and `symlink_metadata("\\?\C:")` is `ERROR_INVALID_FUNCTION` — a prefix is an
anchor, not an entry. The fixtures reach it via `temp_dir().canonicalize()`,
which returns the verbatim `\\?\C:\...` form, so every `--contract`, `--bundle`
and artifact read failed closed. Failing closed is the right direction; it
refused everything.

The walk now stats only `Component::Normal`, skipping the prefix and the root.

> **Security impact: this does not widen access.** Every named component is still
> inspected and still refused if it is a symlink; the `ParentDir` rejection is
> untouched and still runs first. What is skipped is the prefix and the root — on
> Windows unstattable, on Unix `/` — neither of which can be a symlink
> redirecting the walk. Nothing that was refused before is accepted now.

Proving that needed a new test, because the existing coverage did not hold the
function down: with the component walk disabled outright, every test in the file
still passed. A symlinked *final* component is already refused by the
regular-file check in `read_regular`, and a symlinked artifact *directory* by the
`escapes-root` check in `checked_child`. The gap is a symlinked **intermediate
directory** on `--contract`, which takes an arbitrary path under no root — there
the walk is the only guard. The new test covers exactly that, and was verified to
fail when the walk is disabled and pass when it is not.

**Six portability defects in the devmap crates.** Windows Clippy had failed since
its first run on 2026-09-11 and Build/Test since 2026-09-13, on defects unrelated
to the CRLF class: `PermissionsExt::from_mode` and `std::os::unix::fs::symlink`
in `digest_cache` tests; `parse_etime`, reachable only from `stale_server_warning`'s
unix arm and therefore dead code on Windows (with a `needless_return` in the one
body where that arm *is* the whole function); `serving_or_dead`, whose six callers
are all `cfg(unix)`; an `inventory.rs` test module whose `use super::*` had nothing
to name; and a `Write` import in `worktree_stress` used only by `ipc_unix`. Each is
now gated to match what actually calls it. The read-only-directory test is gated
whole — Windows denies writes through ACLs, which `std::fs` cannot set — while the
symlink shapes are gated *inside* their test so its directory case still runs
everywhere.

### 3. A commit, branch switch or rebase could go unseen by the daemon

The daemon's git-HEAD sentinel never reached the pending queue.
`canonical_pending_entry` short-circuits control tokens correctly, but it
returned them as `PendingEntry::Canonical`, and
`enqueue_pending_paths_under_root` then ran the K7 build-cache check on the
result. `root.join("\0devmap:git-head-changed")` cannot be handed to the OS — a
path string cannot carry an interior NUL — so `is_cache_directory` returned
`Err`, and the `Unreadable` verdict refused the token at the door with
`enqueued 0 changed path(s)`.

So HEAD moved and the daemon never learned. It is why `rust.yml`'s *Native
worktree capacity and process recovery* step failed on macOS and Ubuntu alike,
the harness waiting out its full 90 s deadline for a stored HEAD that could never
move.

Every existing test of the sentinel called `enqueue_pending_paths`, which has no
cache check, while the daemon calls `enqueue_pending_paths_under_root`, which
does. The suite was green against a producer the daemon does not use.

Fixed as a type rather than a fourth guard: `PendingEntry::ControlToken` makes
`Canonical` mean "a repo-relative path" and nothing else, and forces every caller
to branch — so the next path-shaped check cannot swallow a control token in
silence. `reconcile_pending_paths_with` drops its separate `is_control_token`
pre-check and handles the variant instead, leaving one owner of the rule.

### 4. The serve stress test drains until the work settles, instead of once

`fifty_spawn_retire_cycles_and_a_kill_mid_drain_leave_the_store_usable` failed on
CI under load (run 34904461297 attempt 1, green on attempt 2 of the same commit)
and reproduced locally under `verify.sh`'s whole-workspace load.

It is not a timing flake. The abort does not terminate the killed daemon's own
`spawn_blocking` drain, so two drains are live. When the surviving one touches a
row this one has already claimed, that row's revision moves, and
`clear_claimed_pending_paths` deletes `WHERE path = ?1 AND revision = ?2` — the
acknowledgement matches nothing and the row stays. That is the store working as
designed, the same rule `equal_clock_ticks_cannot_acknowledge_a_new_edit` pins: a
drain must not retire an edit that arrived after it looked. The work is in the
generation; the row is merely *unretired*, and only another drain retires it. A
daemon does that on its next idle tick; this test has no daemon left.

Waiting cannot substitute, and a first attempt proved it: with nothing draining,
60 s of sleep reported `late.py indexed=true, still queued=["late.py"]`
unchanged. The test now drains until the queue is empty. The property is
unchanged and still fails closed — `late.py` ends in the generation and out of
the queue, or the bound expires and the message names what it saw, so the next
failure is diagnosable rather than a rerun.

### 5. The index now speaks once at the first navigation tool call

Across 37 measured sessions, 36 made **zero** DevMap queries. The `SessionStart`
briefing is read once and then scrolls out of context, so by the time an agent
reaches for `Read` or `Grep`, the index is out of mind.

`devmap hook pre-tool-use` is a new hook event that restates the directive once
per session, at the first navigation tool call, and stays silent when the index
cannot answer.

It is deliberately **not** installed by `devmap integrate`. On Claude Code and
Cursor, `PreToolUse` decides an authorization outcome, and `claude::hooks_block`
refuses to emit a handler onto any such event: a code index has nothing to
contribute to a permission decision, and a table that could place one there is
one edit away from widening what this tool can approve. Wiring it is therefore a
deliberate, hand-made choice in your own host configuration:

```json
"PreToolUse": [{ "matcher": "Read|Grep|Glob", "hooks": [
  { "type": "command", "timeout": 5,
    "command": "\"/abs/path/to/devmap\" hook pre-tool-use" }]}]
```

The handler only ever emits `additionalContext`, never a decision field, which
`pre_tool_use_never_emits_a_permission_decision` asserts against the document it
actually produces.

Cursor is the exception that proves the rule: its `preToolUse` **is** a
permission hook, where a schema mismatch blocks the tool outright. So
`devmap integrate` installs the same handler on Cursor's `postToolUse` with a
`Read|Grep` matcher — the directive arrives after the first read instead of
before it, and cannot block anything. A test asserts the written
`.cursor/hooks.json` names none of `preToolUse`, `beforeReadFile`,
`beforeShellExecution`, `beforeMCPExecution`, `beforeTabFileRead` or
`subagentStart`, and sets no `failClosed` — which would turn a crash into a
blocked `Read`.

`render_host_stdout` replaces the ad-hoc `additionalContext` unwrapping in
`run_hook_command`, so each host gets the stdout shape it actually parses, from
one owner.

27 conformance tests cover both hosts: once-per-session under concurrency,
bounded markers across many sessions, hostile characters in the briefing,
never blocking a tool call, and no permission decision in the emitted document.

`.mcp.json` now registers the stdio server they expect.

The accompanying `.devcouncil-skills.json` refresh is the manifest

### 7. The MCP server reported version 0.1.0 through three releases

`serverInfo` is the one field through which every host learns which build
answered it, and it had been sitting at `0.1.0` while the product went to 0.2.3.

The cause is structural, not a typo. `devcouncil/mcp` cannot import `package
main`, so it could not read the host's `Version` constant and was written with
its own literal instead. Nothing could have caught the drift, because there was
no shared constant for it to disagree with — two literals that must agree, in
packages that cannot see each other.

`devcouncil/version` is now the single Go-side owner, `cmd/devcouncil`'s
`Version` is an alias rather than a second literal, and `dcgrep`, `dcstore` and
`dcverify` each report the workspace version through a `component_version` test
per crate that pins the *binary's* reported version against the manifest rather
than against a copy of it. `scripts/check-release.mjs` gained the Go arm: it
parses `devcouncil/version/version.go` and compares it with package.json,
package-lock.json, the Rust workspace version and the tag before any build
minutes are spent.

### 8. The plugin bundle showed a slug, and had nowhere to put a mark

The plugin list showed `devmap` beside products that showed a name, because
`name` is the install identifier and has to stay a kebab-case slug.
`displayName` is the only field Claude Code renders as a human name. It is set
in both the plugin manifest *and* the marketplace entry, because the browser
reads the entry's own copy — setting one and not the other leaves the slug on
screen.

The logo could not go in the portable manifest at all. Claude Code documents no
field for one, and the Agent Plugins 1.0.0 schema sets
`additionalProperties: false`, so the key makes a conformant client reject the
package. Cursor is the only one of the three hosts that renders a `logo`, so the
mark lives in `.cursor-plugin/plugin.json` and the bytes ship through
`include_bytes!` — a `cargo install` binary carries no repository beside it, and
a manifest naming a logo that was never written is worse than one with no logo.

Validation now follows the file rather than one key set. The bundle emits three
manifests in three dialects, and checking all of them against Claude's keys
reported the emitter's own Cursor manifest as wrong: a warning correct about
Claude and false about the file it was aimed at, which is how a warning list
stops being read. `ManifestDialect::of_path` picks the dialect from the
directory, defaults to the stricter Claude set when provenance is unknown, and
the diagnostic names which host ignores the field.

### 9. A `--json` contract gate had been running nothing and reporting `ok`

`dc-verify`'s json_contract calls `skip_or_fail` no longer. Its manifest had
named a Python module deleted in 3286db5, and turning the skip into a failure
needed `DC_JSON_REQUIRE_CLI=1`, which no workflow ever set — so for four days
the gate ran nothing and reported `ok`.

It now drives the real Go host as a process for every invocation in
`json_stdout_manifest.tsv`, and a missing binary, an unscaffoldable project or a
harness that could not start all *fail*. No in-process test can settle this: the
Python `CliRunner` it replaced merged the two streams, so a banner leaking onto
stdout was indistinguishable there from one going to stderr — which is how `dev
cost budget --json --set 5.00` shipped emitting unparseable stdout with a green
suite. The Go host's own handler tests swap `os.Stdout`, which is closer but
still cannot see what `console.Session` renders around the handler. Two real
file descriptors settle it.

Running the manifest against the host found a real defect, which is fixed here:
`dev hook status` and `dev hook disable` took the protocol bypass along with the
retired lifecycle events that share the word `hook`. An event call must stay
inert, but those two are ordinary commands a person or a script runs, and
`--json` owes them one JSON value on stdout like any other. Only the session can
keep that promise where the handler has no receipt to write —
`integrate.Uninstall` returns none for an unsupported `--client`, and the bypass
left stdout empty while a caller was parsing it.

### 10. A directory of tests nobody ran

`tests/unit/test_devmap_skill_delivery.py` imported `devcouncil.cli.main` and
`devcouncil.skills.registry`, both deleted in 3286db5 when the orchestrator
moved to Go. It could not be imported, let alone pass, for months, and nothing

Its assertions are ported to the two ports that now own them —
`devcouncil/skills/delivery_test.go` and `cmd/devcouncil/skills_cli_test.go` for

`tests/unit/`, and a README records the rule that makes this non-recurring:
anything added there must be run by a workflow, because a test nobody runs
reports the same result as a test that ran and passed.

### 11. The local gate chain was red by construction

Section 9's gate is a fixture-carrying test, and the workflows that run it
gained a `go build` step for the host. `rust/verify.sh` did not, and its gate 3
is `cargo test --workspace` — which includes that crate. So every local run of
the chain failed two tests on a message about a missing path: measured here
before the fix as `VERIFY_EXIT=101`.

`verify.sh` now builds the host the way `analysis-plane.yml` and `rust.yml` do,
honours `DEVCOUNCIL_BIN` when it is set, and names a missing Go toolchain itself
rather than letting it surface as two gate-3 failures about a path. The module
has no third-party dependencies and links in about a second, so gate 3 pays
nothing and no tree-sitter grammar is compiled for it. `scripts/ci-local.mjs`
runs `./verify.sh --quick`, so it is covered by the same change rather than
needing its own copy; `rust.yml`'s workspace job already excludes `dc-verify`
and was never affected.

### 12. The gates are now measured, and a diff is asked whether it says anything

Five borrows from a comparison against reverify, which makes deterministic tools
the judge of a model's claims about a binary. DevCouncil's subject is a change
rather than an artifact, so the mechanisms differ; the epistemology is the same,
and these are the places it had not yet been applied.

**The gates are measured as classifiers.** `dc-verify/tests/corpus/cases.txt` is
23 diffs, each declaring what *every* gate must say about it — so a fixture
written for `secret_scan` is a standing negative control for `stub_detection`.
`false_accept.rs` prints a confusion matrix and fails the build on a single
false accept or false positive: currently **0 and 0** over 12 known-positive and
34 known-negative expectations. It was falsified in both directions before
landing — raising the AWS key floor by one character reports a FALSE ACCEPT, and
removing the comment guard reports two false positives.

**A substance measurement.** Every other gate asks whether something is *wrong*
with a change; none asked whether there is anything *in* it. A diff of relocated
functions, braces and a regenerated lockfile trips nothing and arrives as
`findings: []`. Added lines are now classified substantive / trivial / moved /
repeated / generated, the classes partition the total, and no ratio goes on the
wire so a consumer always sees the denominator. It never blocks: a pure refactor
measures low by construction, and that is the correct reading of one. The 1/4
threshold is measured rather than chosen — 200 commits of this repository, 161
judged, median 0.68, 5th percentile 0.40, and the single commit below it is a
version bump that is 141/182 regenerated `Cargo.lock`. Reproduce with
`rust/tools/substance_calibration.sh`.

**A strength axis on findings.** Severity says how much a finding matters;
strength says how much it can be trusted — proven / observed / derived. Both
findings gates report `derived`, because `secret_scan` matches a credential's
*shape* and `stub_detection` matches *text*. That is an accurate and
uncomfortable description of the rigor layer, which is exactly why it belongs on
the wire: this repository's standing rule that a check which could not run must
not look like one that ran, carried one step further — a guess must not look
like a measurement.

### 13. A successful checkout handed every agent six tools this host does not serve

`AllowedNextTools` in `devcouncil/lease.go` still spelled out the retired Python
host's surface. Every task checkout answered with eight tool names, and six of
them — `devcouncil_read_file`, `devcouncil_get_evidence`, `devcouncil_run_command`,
`devcouncil_apply_patch`, `devcouncil_write_file`, `devcouncil_update_task_scope`
— are served by nothing here. Checked against the registry on `main`: only
`devcouncil_get_diff` and `devcouncil_verify_task` of that list exist. An agent
that did what the checkout told it to do next called into a tool the host does
not have.

This is `GAP-P7-NEXT-TOOLS-DRIFT`, which the *verify* path was corrected for
earlier in this release. The checkout path kept its hand-written copy because,
unlike verify's, nothing held it to the registry. Two lists spelled separately
drift; that is not a prediction, it is what happened twice.

The fix is at the canonical owner rather than the call site. `Specs()` and the
new `ServedToolNames()` both read one literal list, `toolSpecs()`, so the served
surface cannot be restated anywhere inside the package. `verify.AllowedNextToolsForVerify`
still keeps a copy — `devcouncil` imports `verify`, so reading back would cycle —
and that copy is safe only because `allowed_next_tools_test.go` holds it to this
list in both directions.

The stored envelopes under `testdata/golden/{cli,mcp}/lease/` had recorded the
wrong list for as long as it was wrong, without ever contradicting it, because
nothing replays them. They are re-recorded here. A golden that is written and
never compared is a description, not a check.

`TestCheckoutAllowedNextToolsAreAllServedByThisHost` enumerates all eight status
values against both gap states rather than sampling one: each status is a
separate branch of the switch, and a branch that is never asked cannot be said to
have passed.

### 14. Three copies of each agent definition, maintained by hand, had drifted onto the same retired tools

The same root cause, one layer up. Each DevCouncil agent existed three times —
`.claude/agents/<name>.md`, the Codex role at `.codex/agents/<name>.toml`, and the
plugin copy — all maintained by hand. Two of the three still told agents to call
`devcouncil_write_file`, `devcouncil_apply_patch` and `devcouncil_run_command`.

Section 13 fixes a list. This fixes the shape that produces the list: the Codex
role and the plugin copy are now *rendered* from the `.claude/agents` definition
by `scripts/sync-agent-defs.mjs`, and `npm run agents:check` reports drift
between the three.

The definitions are now tracked, which is the part worth stating plainly. They
were local state before. On a clean clone an untracked file reads as *missing*,
so the check would have reported the same thing whether the copies agreed or
were absent — and a check that could not run must never report what a check that
ran and passed reports. The `.gitignore` re-inclusions are scoped to those nine
files; `settings.local.json`, `commands/`, `worktrees/` and the rest of the
plugin stay ignored.

Fifteen tests cover the renderer, and the ones that matter are the refusals: an
absent source is refused rather than called "nothing to do", a deleted copy is
reported *missing* rather than skipped, and frontmatter whose name disagrees with
its filename is refused outright.

### 15. A soak that could not write its samples still reported success

All three CSV writes in `rust/tools/soak.sh` were bare redirects. A write that
could not land left `FAILS` at zero, so the soak ran its full cycle count and
reported success over a sample file it had never produced — the failure mode this
repository has a standing rule against.

Each write now propagates. `SoakCsvAdmission` drives all three sites against both
a writable target and an unwritable one.

The test was checked against the *pre-fix* script before it was accepted: all
three blocks exit 0 where the test requires 1. It fails against the code it
describes, which is the only thing that separates a regression test from a
restatement of the fix.

### 16. The generated guide described the code and never mentioned the other sessions in the repository

DevMap answers what the code is. It has nothing to say about the other
worktrees, the running agent sessions, or the file two lanes are both holding —
and an agent that navigates the graph perfectly and then edits a file a sibling
lane owns has still collided. This consolidation found two such files contended
across two worktrees, which is the ordinary state of this repository rather than
an unusual one.

The generated agent guide and the Cursor always-apply rule now open with
`gitpulse_insights` and name the collision, change-context, provenance and ledger
tools, carrying the rule that GitPulse's facets fail independently: a facet that
could not scan is not a facet that came back clean.

`DELEGATION_RULE` exists for a narrower reason. A subagent reads the prompt its
parent wrote, not this file. Without a rule telling the parent to carry both
tools forward, the guide binds exactly one agent and every lane it spawns starts
by grepping.

The four tests quote the guide's wording literally instead of comparing against
the constants they cover. A test that reads the constant under test agrees with
whatever that constant says, which is precisely the property these have to be
able to falsify.

### 17. Learned ranking and lexical search for `dc-grep`

`dc-grep` now supports learned sparse ranking (SPLADE/WordPiece) alongside BM25 lexical ranking.
The indexer and query engines in `rust/dc-grep` and `backend/go_orchestrator/dc/dcgrep` provide:
- Dual-mode index support: standard inverted index with BM25 term weighting and learned vocabulary token weighting.
- WordPiece tokenization with strict token length and count caps to prevent runaway memory use on adversarial queries.
- Integrity verification and tamper resistance on persisted index postings.
- Seamless interop between the Go orchestrator child process and native Rust binary, pinned by comprehensive fuzz and unit tests (`learned_ranking.rs`, `ranked_search.rs`, and Go `interop_test.go`).
- Complete architecture documentation in `docs/lexical-search.md`.

### 18. Navigation nudge expansion for shell read commands

The navigation nudge hook in `rust/devmap-cli/src/hook.rs` sniffed shell search commands (`grep`, `rg`, `find`) but missed agents reading files sequentially via shell commands (`cat`, `head`, `tail`, `sed`, `awk`, `bat`).
However, naive detection of read commands caused false-positive nudges on pipe tails (e.g. `npm test | tail -25`) and configuration or secrets inspections (e.g. `cat .env`).
- Added `READ_COMMANDS` with `segment_reads_source()` checking whether the targeted file matches known programming language extensions in `devmap_extract::languages`.
- Preserved exclusion of destination files in redirects (`> file.rs`) and piped summary commands.

### 20. Raw logs on a work item, kept out of everything that rewrites text

A task's `description` is a drafting surface: `items.enhance` hands it to Manvi
to be rewritten, and `briefs.get` title-extracts from it. A stack trace pasted
there is therefore evidence handed to a paraphraser. GitPulse had been carrying
the fix as a local edit to its vendored copy of this crate, which its own
vendor gate reports as drift and which the next re-vendor would have silently
reverted; it belongs here.

`logs` is a separate field on a work item with its own bound and its own
handling:

- **Bounded at 256 KiB**, matching the terminal output window that produces the
  paste, and the request envelope in `input.rs` rises from 256 KiB to 1 MiB so
  a task carrying a full-size log plus its own fields still fits. Both numbers
  are named constants (`MAX_LOGS_BYTES`, `MAX_REQUEST_BYTES`) rather than
  literals, because the pair only makes sense read together.
- **Preserved when omitted**, exactly as `locked_fields` already is. An older
  host that does not know the field must not wipe evidence a newer one stored;
  only an explicit empty string clears it.
- **Stripped from list payloads.** `json_remove` drops `$.logs` alongside
  `$.description` and `$.acceptance_criteria` in the card query, so a board
  listing does not carry a terminal dump per row.
- **Stripped from the enhancement source.** `items.enhance` removes `$.logs`
  before building the input, so rewriting a title cannot send a log to Manvi.
  This is the whole point of the field existing.
- **Fenced by measurement, not by assumption.** Logs reach the brief's markdown
  inside a code fence whose backtick run is computed from the longest run in the
  text itself, so a log containing ``` cannot break out of its own fence.

Four tests in `workbench/logs_tests.rs` cover the round trip through
`items.put`/`items.get`/`briefs.get`, the preserve-on-omission and
clear-on-empty pair, refusal of NUL bytes, wrong types and oversize, and that
an enhancement source never carries logs.

### 22. Markup and Stylesheet Indexing (DevMap)

**The reported gap.** On a current index of GitPulse (149 Svelte components),
`devmap search toggleAddMenu` returned the `<script>` function while
`devmap search data-add-repo` and `devmap search nav-heading` returned 0 hits with
`truncated=false` — an empty answer, on a built index, about two names
`TaskBoard.svelte` plainly declares. The cause was structural rather than
Svelte-specific: `devmap-extract` routed only `<script>` regions back through a
grammar, and `html`/`css` sat in `fallback::NON_DECLARATIVE_LANGUAGES`, so the
markup and `<style>` halves of **every** template file, and the whole of every
standalone `.css` and `.html` file, were indexed nowhere.

- **New reader (`devmap-extract/src/markup.rs`)**, serving `.svelte`, `.vue`,
  `.astro`, `.liquid`, `.html` and `.css`/`.scss`/`.less` from one owner:
  - `SymbolKind::MarkupAnchor` — an identity markup declares (`id="x"` → `#x`, a
    `data-*` attribute → `[data-x]`).
  - `SymbolKind::StyleRule` — a name a stylesheet declares: each named component
    of each selector, `@keyframes`, and custom properties.
  - `ReferenceKind::Selector` — a use: a `class` attribute, a Svelte `class:`
    directive, a spec-defined IDREF attribute (`for`, `aria-controls`,
    `aria-labelledby`, …), a `var(--x)` read, and a selector string in a script.
  - Names carry their sigil, so the FTS `unicode61` tokenizer answers
    `data-add-repo` and `nav-heading` with no store or schema change.
- **Resolution is a separate namespace with its own two-rung ladder.** A
  `Selector` never enters the code ladder: its unique-global rung would bind a
  class called `menu` to `function menu` at `HIGH` confidence. Rungs are
  *this file* (`SameFile`, deterministic) and *exactly one declaring file*
  (`Resolution::UniqueSelector`, persisted under the existing `UniqueGlobal`
  label, so no schema or stored generation changes meaning). Cross-file resolution
  additionally requires the declaration to be global (`.css`/`.html`) or the name
  to be an `id` — a component's `<style>` is scoped, so a class it declares cannot
  style another component.
- **Neither new kind is a dead-code candidate.** A class reaches an element
  through `class={expr}`, `classList.add(name)` or a template string, none of
  which this reader follows: it can prove a name is used and cannot prove one is
  not. DevMap therefore does not report unused CSS, and says so.
- **Unresolvable selectors are not filed as failed code attributions.** A class
  whose rule lives in a global stylesheet outside the tree, a framework, or a CDN
  is the ordinary frontend case; 0 selector rows reach `generation_unresolved`.

**Measured (GitPulse frontend, 933 files).** 921 new symbols (688 `StyleRule`,

### 23. Dead-Code Audit: every confident finding on this repository was false

With the markup reader landed, `devmap --json dead` was run over DevCouncil itself
and every finding in the confident tier (0.9) was checked against source. All
**eight** were false positives, from two unrelated causes, and both are fixed here.
The confident tier is the one a reviewer is meant to act on, so a false positive in
it costs more than a missing finding: it proposes deleting live code.

**Six were Python module-level values mistaken for re-export aliases.**
`python_module_aliases` exists so `TestEvidence = VerificationEvidence` survives the
`__all__` filter — it is a name twenty other modules import, and dropping it left
those bindings resolving against a file that, as far as the resolver could see,
declares nothing of the sort. Its guard on the right-hand side was
`matches!(right.kind(), "identifier" | "attribute")`, which asks only what the
*outermost* node is. `OUT = Path(__file__).resolve().parent / "out"` is an
`attribute` whose object is a `call`: it passed, was emitted as a symbol, and then
had no possible caller, because nothing can import it. Measured on this repository
before the fix, 54 of 54 Python `Variable` symbols were computed values of this
shape. After: 3, and all three are real aliases — `SEM = S.SEM`,
`PROJECT = S.PROJECT`, `DEFAULT_MONITOR_MODEL = DEFAULT_OPENROUTER_MODEL`.
`is_python_dotted_name` now walks the `object` chain and admits a node only if every
step of it is a name, iteratively, because an adversarially deep `a.b.c.…` must not
overflow the stack.

**Two were Go functions used as values rather than called.**
`Command{Run: runStatus}` never writes `runStatus(...)`. The extractor records the
mention as a bare `ReferenceKind::Name`, and `resolve_reference` returns `None` for
a bare `Name` rather than continuing down the ladder — deliberately, because the
unique-global rung would bind `except Exception as e` to some unrelated `def e`. The
Go package rung sits *below* that refusal and its comment says as much in as many
words, so the fix is on the liveness side, where the epistemic state can be stated,
rather than by widening a ladder whose own documentation forbids it.
`GO_VALUE_MENTION_REASON` exempts a `SymbolKind::Function` when some **other** file
of its own Go package names it in value position with no receiver. Each clause is
load-bearing and tested: the declaring file is excluded because a same-file mention
is answered by the same-file rung and is live by an edge, with no exemption involved;
a receiver means the reference is a member access (`cfg.runDoctor` names a struct
field); the package join is exact by Go's own visibility rule, since an unexported
name resolves only within its directory and an exported one is spared earlier; and
methods are excluded because a method is reported under `Type.Method`, so matching a
bare mention would mean stripping the type, which over-exempts every same-named
method of every type in the package.

The one **over-approximation is named and tested rather than left to be discovered**:
Go spells a composite-literal field key as a bare identifier with no receiver, so
`Command{run: nil}` is indistinguishable at this layer from naming a package-level
`func run`. An unexported function colliding with a field key is therefore exempted
although nothing uses it. That is the direction an exemption may be wrong in — it
withholds a finding it cannot prove rather than asserting one it cannot support —
and narrowing it belongs in the extractor, where a field key could carry its
composite type as a receiver.

Scope is Go on purpose, not by omission. Outside Go, a cross-file use requires an
import, so the same-file and import-scoped rungs already answer it; Go's package
block is the construct that makes a cross-file mention neither. Whether Kotlin's
top-level functions have the same gap is unmeasured and is not claimed here.

**Result on this repository:** confident non-exempt dead findings 8 → 0. Total rows
48 → 46, every remaining row at 0.4 — the degraded tier, which already says the
answer is not confident. Repository-wide, the new exemption fires exactly twice, on
`runDoctor` and `runStatus` in `internal/mapcli/commands.go`, with no collateral
exemption anywhere else.

**Verification.** 10 new tests. `a_computed_module_binding_is_not_an_alias` pins the
two Python shapes apart in one file, so a future widening of the guard cannot pass by
only checking that real aliases still survive. The nine in
`devmap-analyze/tests/go_function_value_liveness.rs` were confirmed to fail against
the unmodified analyzer; besides the subject and each guard clause, they include an
order-independence property — the same corpus walked forwards and reversed must give
