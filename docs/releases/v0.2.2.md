# DevCouncil v0.2.2 Release Notes

DevCouncil v0.2.2 and DevMap v0.2.2 are the same product version. The npm package,
the Go host (`devcouncil` / `dev`), and the Rust workspace (`devmap`, `dcstore`,
`dcverify`, `dcgrep`) all report **0.2.2**.

This is a performance and durability release. It makes both halves of the build
materially faster — the resolver's import pass and the store's write path — makes
the store materially smaller, and closes five correctness gaps that audits of
those paths uncovered, four of which no existing test could see.

The store schema advances from **20 to 22**. Existing stores migrate in place on
first open; no rebuild is required.

## Highlights

### 1. Go import resolution stopped rescanning the repository

Three call sites answered "which files sit directly in this directory" by
scanning *every* key of `file_symbols` and calling `parent_dir` on each:
`go_files_in_dir`, the package-suffix fallback in `resolve_go_import`, and
`files_in_dir_with_extensions`. Go import resolution calls the first up to four
times per import, so the cost was O(imports × files in the repository) — and
`parent_dir` allocates twice per call, through `Path::parent` and
`to_string_lossy().replace()`.

Measured with `sample(1)` on a 1,942-Go-file tree: 623 of the 825 samples in
`resolver:index` were this scan, 267 of them inside `parent_dir` alone, and the
pass was 29% of an incremental build.

One `files_by_dir` index, grouped once per pass at the point where
`file_symbols` is already complete, turns all three scans into lookups:

| | before | after | |
|---|---|---|---|
| **`resolver:index`** | 1.058 s | 0.212 s | **5.0x** |
| touch build (total) | — | — | **−29%** |
| cold build (total) | — | — | **−13%** |

`code_graph.json` and `repo_map.json` are **byte-identical** across five corpora.
The index is built from `file_symbols` rather than from the extractions, so it
holds exactly the population the scans walked — `file_symbols` takes an entry per
extraction unconditionally, including files that declare no symbol.

The remaining `go_package_dirs` walk is still O(files), but it is reached only by
the suffix tier and measures 1.4% of the build. It was left alone deliberately
rather than traded for a second structure to keep in sync.

It was found with `sample(1)` after two hand-instrumented hypotheses had each
blamed the wrong loop — the second because the timer's span silently included
the import loop it was meant to exclude.

### 2. The ledger stores integers where it stored strings

`unresolved_rows` repeated three text columns on every row — the source file, the
reason, and the classification — for what is, on a large repository, hundreds of
thousands of rows drawn from a handful of distinct values. Schema **v22** interns
those three columns into a shared `unresolved_texts` pool and stores three
integer ids in their place. Schema **v21** drops two indexes that no production
statement filters on.

Measured on this repository (1,094 files), min of five runs, interleaved, against
a binary built from the previous tip:

| phase | before | after | |
|---|---|---|---|
| **persist:write** (cold) | 0.7525 s | 0.5423 s | **1.39x** |
| unresolved (cold) | 0.4279 s | 0.2264 s | **1.89x** |
| commit (cold) | 0.0878 s | 0.0665 s | 1.32x |
| total (cold) | 1.9852 s | 1.7924 s | 1.11x |
| **persist:write** (warm) | 0.2017 s | 0.1750 s | **1.15x** |
| unresolved (warm) | 0.1256 s | 0.1001 s | 1.26x |
| total (warm) | 0.7104 s | 0.6666 s | 1.07x |

On-disk store size falls from **155.1 MiB to 129.9 MiB** for the same content.

### 3. What this costs the reader, stated plainly

Interning is a trade, not a free win. The `generation_unresolved` view now
resolves three `INTEGER PRIMARY KEY` lookups per row that the flat table did not
perform at all:

| query over the view | v20 | v22 | |
|---|---|---|---|
| `COUNT(*)` | 0.015 s | 0.047 s | 3.19x |
| project all six columns | 0.108 s | 0.157 s | 1.45x |
| the same, ordered | 0.111 s | 0.149 s | 1.34x |

This is accepted rather than unnoticed. No production statement in the workspace
scans the whole view, no crate outside `devmap-store` reads the relation, and the
two callers that touch it are test-only or `LIMIT`ed. The measurements and the
reason the three joins are deliberately **not** `LEFT` joins — an inner join makes
a row with a dangling id fail a count, where a left join would hand the reader a
plausible `NULL` — are recorded next to the migration in `rust/devmap-store/src/schema.rs`.

### 4. Four correctness gaps closed, each demonstrated red

Thirteen tests were added. Each one was shown to fail against mutated code rather
than assumed to be load-bearing.

- **The per-row path memo had no multi-file fixture.** Every fixture row in the
  ledger suite carried the same source file, so replacing the memo's guard with
  `true` — which attributes every unresolved call in a repository to the *first*
  row's file — left the entire `devmap-store` suite green. Found by mutation
  testing, not by inspection; a classification memo three lines above it had the
  same shape and had been checked by hand.
- **`AUTOINCREMENT` was an unguarded correctness requirement.** v22 digests are
  taken over `paths` and `unresolved_texts` ids, so an id reused after a prune
  could match different text and leave stale rows live. Schema checks verify
  column names, not constraints; there is now a behavioural test that inserts,
  deletes, and re-inserts, and requires the second id to exceed the first.
- **The gate scripts embed SQL that no test parsed.** A migration broke
  `memory_model_probe.sh` while `cargo test --workspace` stayed green across 303
  test binaries. Every SQL statement the gate scripts embed is now parsed against
  the current schema, over a glob of the scripts rather than a hand-maintained
  list.
- **A `devmap-cli` fixture wrote a column v22 drops**, which the migration would
  have surfaced only at gate time.

### 5. The differential write's carry-forward guards got tests

`save_generation_timed`'s carry-forward is an optimisation carrying a correctness
obligation: every row it declines to rewrite, it must instead be able to reuse
*exactly*. Four of its decisions guard against a caller whose `affected_paths`,
`deleted_paths`, and extraction slice do not agree with each other — and each was
reachable by mutation with the whole suite green across 101 test binaries. A guard
nothing exercises is indistinguishable from a guard that is wrong.

The guards are not hypothetical: the two writers disagree about what a
differential write even contains. `devmap build` hands over an extraction for
every scanned file, while the daemon hands over only the files it re-read. Every
carry-forward has to be right for both shapes, and the partial shape — the
daemon's — was the one no test reached.

A new suite names the mutation each test refuses. It is gated on the `parse`
feature rather than listed as feature-off-safe, because with `parse` off no
payload identity can be computed, nothing is ever carried, and the write is
refused outright before reaching the decision under test — the tests would not
merely fail to compile, they would assert something else.

### 6. The daemon says when it is serving, instead of being guessed at

`Daemon::wait_until_serving` is a latched watch channel tripped the moment the
IPC endpoint is live. The socket-path polling it replaces was wrong in two ways
that cost a gate its credibility:

- It **cannot see a daemon that stopped.** A `run_loop` that returned an error or
  panicked before binding leaves the path missing for exactly the same reason a
  slow startup does, so the waiter blamed the clock. Measured on an idle machine,
  a poll bounded at 500 × 20 ms turned `devmap IPC endpoint is already active` —
  a daemon that failed in milliseconds and said precisely why — into 11.5 s of
  waiting followed by "it did not bind in time".
- It **cannot see an endpoint that came up and was released** between two polls,
  which every short-idle daemon in this crate's tests does by design.

The signal is latched rather than levelled and never cleared, because the
endpoint's *release* is an ordinary part of a daemon's life — every retirement
path unlinks the socket. What a caller needs to know is that startup reached a
live endpoint, which is a fact about the past and cannot stop being true.

It is not a substitute for watching the task: a caller that wants a *bounded* wait
still has to race this against the handle `run_loop` runs on, because a daemon
that died before binding never reaches the signal at all. `serving_or_dead` — in
the file's test module for unit tests, and in `tests/support/mod.rs` for the
integration tests, which cannot see inside the library — is that race written out.

## Upgrade

Stores at schema 20 or 21 migrate in place on first open. The whole migration
ladder runs inside a single immediate transaction, and the v22 rung refuses and
rolls back if the row count changes across it.

Upgrade equivalence was verified end to end on four repositories spanning Go,
TypeScript, TSX, Python, Rust, Svelte, and JavaScript: the previous binary wrote
a store, the new binary migrated it in place and built over it, and the result
was compared against a cold build from scratch. All four were **byte-identical**,
across 1,214,003 ledger rows in total — DevCouncil 181,749, GitPulse 403,913,
Manvi 83,533, scholarlm 544,808.

### The last branch was merged

`f491566` merges `claude/devmap-unresolved-calls-ff83ca`: five commits,
1,842 insertions across `devmap-extract` and `devmap-resolve`, three of the five
commits and 48 of the added test functions being tests. It closes four
attribution defects in the call extractor and resolver:

- **A call was counted as two attribution sites.** One call produced two entries
  in the unresolved ledger, inflating the coverage warning DevMap reports about
  itself, and letting `Vec` be attributed as a value rather than a type.
